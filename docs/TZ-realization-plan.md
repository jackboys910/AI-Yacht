# План реализации ТЗ nazarov.net

**Источники требований:** `docs/TZ-nazarov-net-v3.docx` (версия 3.0 от 27.09.2026)
и `docs/TZ-nazarov-net-v4.md` (версия 4.0 от 06.11.2026 — сообщество, роли,
главная на букве S). Где v4 и v3 расходятся, побеждает v4.
`docs/TZ-nazarov-net.md` (версия 2.0) оставлен как история — расхождения разобраны в разделе 2.

**Исключено по решению заказчика:** онлайн-оплата Stripe (депозит, payment links, waiver).
Это этап 2, в текущей реализации не делаем и не закладываем, но модель данных
поездки оставляем расширяемой, чтобы потом не переделывать.

**Порядок работ подчинён приоритету:** сначала админка и сборка страниц на нынешнем
дизайне (этап 1, показан заказчику), затем сообщество и роли по ТЗ v4 (этап 2 —
это следующее демо), и только после — рассылки, счётчики и остальное.

## 1. Как мы работаем

Один пункт плана = работа в ветке `dev` = коммит = pull request `dev → main` = merge
commit. Следующий пункт начинается только после того, как предыдущий влит.

Каждый пункт закрывается по одному и тому же шлюзу проверки. Пункт не считается
сделанным, пока весь шлюз не зелёный:

| Проверка | Команда | Что ловит |
| --- | --- | --- |
| Типы | `npx tsc --noEmit` | ошибки типов, несобранные пропсы, забытые ключи словарей |
| Линт | `npm run lint` | неиспользуемое, правила Next.js |
| Сборка | `npm run build` | падения статического экспорта, ошибки пререндера |
| Вывод сборки | поиск по `out/` | что нужные страницы реально появились, а черновики — нет |
| Сценарий | Playwright по `out/` через локальный статический сервер | что страница работает в браузере, без ошибок консоли |
| Вёрстка | Playwright: ширины 320 / 360 / 390 / 768 / 1024 / 1440 | горизонтальная прокрутка и «поехавшие» блоки |

Playwright уже установлен локально (`node_modules/playwright`), импорт —
`file:///F:/Yacht/node_modules/playwright/index.mjs`. Проверять сборку `out/` нужно
маленьким статическим сервером, а не `next dev`: HMR-вебсокет дев-сервера подвешивает
закрытие контекста Playwright.

Деплой на боевой nazarov.net запускает George вручную через GitHub Action
«Deploy to Cloudflare». Сами мы не деплоим ничего.

## 3. Архитектура: принятые решения и почему

### 3.1. Сайт остаётся статическим, данные приезжают на сборке

`next build` с `output: "export"` читает Firestore и печатает готовый HTML для каждой
опубликованной поездки. Это даёт быстрые страницы, работающие превью ссылок в соцсетях
и нормальную индексацию — то, ради чего в ТЗ стоят критерии Т-01, Ш-03, Ш-05.

Следствие, с которым живём осознанно: между «Опубликовать» в админке и появлением
страницы на сайте проходит время пересборки. В ТЗ это зафиксировано как 5 минут
(критерии А-08, А-09).

Что этому не мешает:

- **Предпросмотр** (А-07) рисуется в админке теми же React-компонентами из черновика,
  без всякой пересборки. Заказчик видит результат сразу.
- **Счётчики Going / Interested** подтягиваются в браузере после загрузки страницы,
  поэтому не устаревают между сборками.
- **Переход Upcoming в Past** обеспечивается ежедневной пересборкой по расписанию
  (cron в GitHub Actions), как и записано в Приложении А ТЗ.

### 3.2. Серверные точки входа — на Cloudflare Worker, не на Firebase Functions

Сейчас Cloudflare отдаёт только статику (в `wrangler.jsonc` нет `main`). Добавляем
воркер-скрипт: статика по-прежнему отдаётся напрямую с edge и воркер для неё не
запускается, а воркер обрабатывает только `/api/*`.

Зачем это нужно:

| Точка входа | Зачем |
| --- | --- |
| `/api/subscribe` | проверить Turnstile и записать подписчика, не открывая Firestore на запись всему интернету |
| `/api/interested` | то же для кнопки «I'm interested» |
| `/api/application` | заявка на поездку |
| `/api/solutions` | заявка Solutions |
| `/api/rebuild` | по кнопке «Опубликовать» дёрнуть GitHub Action пересборки, храня токен в секрете воркера |
| `/api/capi` | серверные события Facebook (Conversions API) |

Почему не Firebase Cloud Functions: они требуют тарифа Blaze с картой. Cloudflare
Workers на бесплатном тарифе дают 100 000 запросов в сутки, и запросы к статике в этот
лимит не попадают. Дополнительных расходов не возникает — Приложение Б ТЗ не меняется.

Воркер ходит в Firestore по REST API от имени сервисного аккаунта (JWT подписывается
Web Crypto прямо в воркере). Благодаря этому правила Firestore закрывают запись из
браузера полностью.

### 3.3. Права доступа к Firestore

| Кто | Что читает | Что пишет |
| --- | --- | --- |
| Аноним: сайт и сборка | опубликованные поездки, интересы, люди, настройки, проекты Our work, счётчики | ничего |
| Владелец: вошёл в админку | всё | всё |
| Воркер: сервисный аккаунт | всё | подписчиков, заявки, счётчики |

Подписчики и заявки не читаются анонимно никогда — иначе чужая база email утекает
одной строкой в консоли браузера.

### 3.4. Админка на статическом экспорте

Адрес один: `/admin/`. Внутренняя навигация — через строку запроса
(`/admin/?view=trips&id=...`). Так перезагрузка страницы и сохранённая ссылка работают:
Cloudflare всегда отдаёт `out/admin/index.html`, а строка запроса на выбор файла не
влияет. Вложенные адреса вида `/admin/trips/abc` на статике дали бы 404.

Админка целиком клиентская, в сборку сайта её данные не попадают. `useSearchParams`
в статически отрендеренном маршруте требует обёртки `<Suspense>` — учтено.

### 3.5. Один рендерер поездки на три места

Компоненты страницы поездки принимают на вход объект `Trip` и используются:

1. на публичной статической странице `/sailing/<slug>/`;
2. в предпросмотре админки;
3. при генерации картинки для соцсетей.

Правило «незаполненный блок не показывается» (П-10) живёт внутри рендерера, а не в
трёх копиях.

### 3.6. Что делаем с нынешним лендингом AI Yacht

Его разметка и словари — это и есть образец страницы поездки. По пунктам 1.4 и 1.6
компоненты `hero`, `price`, `program`, `route`, `team`, `faq`, `apply` переезжают
с «текста из словаря» на «текст из объекта Trip». По пункту 1.11 сама поездка AI Yacht
заводится через админку и сверяется со снимками нынешней версии (П-11).

Словари `src/i18n/dictionaries/*` остаются — в них переезжают строки интерфейса из
Приложения В ТЗ.

### 3.7. Права организатора держатся на базе, а не на интерфейсе

Это главное архитектурное добавление v4. До сих пор вопрос «кто это» имел два
ответа: владелец (есть запись в `/owners`) и все остальные. Теперь ответов три, и
третий — организатор — привязан не к человеку, а к поездке: в ней лежит поле
`organizerEmail`.

Принятые решения и причины:

- **Разрешение живёт у поездки, а не у пользователя.** Так его описывают и
  источники: «Organizer is a limited permission granted by an administrator to a
  member for a specific adventure». Один человек ведёт две поездки и не имеет
  прав на третью, и это не требует никакой таблицы ролей.
- **Связка по подтверждённой почте, а не по идентификатору.** Иначе владельцу
  пришлось бы ждать регистрации автора идеи, выспрашивать у него внутренний
  идентификатор и вписывать руками. Правило Firestore сверяет `organizerEmail`
  поездки с `request.auth.token.email` при `email_verified == true`.
  Без проверки подтверждения любой завёл бы аккаунт на чужой адрес и забрал
  чужую поездку — поэтому подтверждение почты обязательно.
- **Запреты описаны списком неизменных полей, а не списком разрешённых.** Правило
  говорит «`status`, `organizerEmail`, `interestId`, `slug`, `createdAt`,
  `publishedAt` должны остаться прежними», и всё остальное организатор правит.
  При обратном подходе каждое новое поле модели молча оказывалось бы закрытым, и
  форма ломалась бы спустя месяцы незаметно для нас.
- **Проверка в базе, а не в панели.** Панель организатора просто не рисует кнопки
  публикации, но даже отправленный руками запрос отклоняется правилом. Интерфейс
  — удобство, правило — граница.
- **Публикация остаётся под владельцем.** Организатор правит содержимое, а на
  сайт оно попадает ближайшей пересборкой — ночной или запущенной владельцем.

#### 0.2. Модель данных и правила предметной области

Чистый TypeScript, без Firebase. Делается до подключения базы, чтобы дальше всё
собиралось вокруг одних и тех же типов.

Появляется:

- `src/lib/content/types.ts` — `Interest`, `Trip`, `Person`, `Subscriber`, `TripApplication`,
  `SolutionsInquiry`, `WorkProject`, `Settings`, `Counters` и все блоки поездки из п. 6.3 ТЗ.
  Двуязычные поля — тип `Localized<T>`.
- `src/lib/content/slug.ts` — адрес поездки из названия (латиница, нижний регистр, дефисы),
  проверка на занятость внутри интереса.
- `src/lib/content/schedule.ts` — `isUpcoming`, `isPast`, сортировки, автоматический статус
  «Completed» после даты окончания. Всё считается в UTC, чтобы сборка и браузер не
  расходились из-за часового пояса.
- `src/lib/content/visibility.ts` — три уровня показа прошедших из п. 6.2 ТЗ и правило

#### 1.7. Черновик, публикация, архив, дублирование

Появляется: список поездок с фильтром по интересу и статусу; действия «Сохранить

Подводный камень: дублирование и фотографии. План предполагал копировать файлы,
чтобы удаление оригинала не выбило картинки из копии. При реализации выяснилось,
что из браузера это невозможно: Cloud Storage отдаёт ссылки на скачивание без
заголовка `Access-Control-Allow-Origin`, поэтому прочитать байты файла нельзя, а
разрешающую политику задают только через `gcloud` или `gsutil`.

**Принятое решение: дубликат разделяет файлы с оригиналом.** Это безопасно,
потому что файлы в хранилище неизменяемы (путь содержит случайный идентификатор,
правка загружает новый файл) и ничего в приложении их не удаляет — удаление фото
из формы убирает только ссылку, иначе отмена правок забрала бы картинку у уже
опубликованной поездки. Уборка осиротевших файлов, когда до неё дойдёт дело,
обязана считать ссылки в любом случае: фотографии из `/assets/` уже общие.

Проверка: полный жизненный цикл поездки в Playwright; черновик и архив не попадают
в `out/` — проверяется поиском по собранным файлам.

#### 1.12. Пересборка сайта по кнопке «Опубликовать»

Требует ручных шагов George (раздел 4).

Появляется: воркер Cloudflare (`src/worker/index.ts`, `main` в `wrangler.jsonc`) с
точкой `/api/rebuild`, которая дёргает `repository_dispatch` в GitHub; отдельный
workflow сборки и выкладки; в админке — индикатор «Сайт обновляется…» и время
последней выкладки; cron ежедневной пересборки для перехода Upcoming в Past.

Подводные камни:

- Токен GitHub не должен попасть в браузер — он лежит в секретах воркера.
- Точка `/api/rebuild` доступна только вошедшему владельцу: воркер проверяет
  ID-токен Firebase.
- Две публикации подряд не должны запускать две сборки — ставим минимальный интервал.
- Добавление `main` в `wrangler.jsonc` не меняет способ отдачи статики: файлы
  по-прежнему уходят с edge, воркер для них не запускается.

Как сделано:

- **Запуск — через `workflow_dispatch`, а не `repository_dispatch`.** Воркер дёргает
  тот же workflow «Deploy to Cloudflare», которым выкладка шла и раньше, и читает
  его состояние для индикатора. Токену при этом хватает права Actions, и доступа к
  содержимому репозитория у него нет совсем.
- **Право нажать проверяет не воркер.** Он спрашивает Firestore про запись
  `/owners/{uid}` под токеном самого обратившегося — ответ даёт `firestore.rules`,
  та же запись, на которой держится вход в панель.
- **Повтор отсекается по состоянию GitHub, без своего хранилища.** Идущая сборка и так
  захватит сохранённое; начатую меньше 90 секунд назад догонять незачем.
- **Имя репозитория — в `wrangler.jsonc`, а не в панели Cloudflare:** деплой заменяет
  обычные переменные, заведённые через панель, а секреты не трогает.
- Ежедневный запуск — расписанием GitHub (01:00 UTC), своего cron у воркера нет.

Подводный камень, который всплыл на проверке: только что запущенная сборка не сразу
появляется в списке запусков GitHub, и первый же ответ после нажатия описывает ещё
прошлую. Без поправки индикатор сразу после нажатия говорил бы «сайт обновлён пять
минут назад» — ровно обратное тому, что произошло. Поэтому запрошенной сборке верим
20 секунд, что бы ни отвечал список.

Что запускает пересборку: публикация и снятие с публикации, сохранение уже
опубликованной поездки, архив и возврат, любая правка направления или человека.
Сохранение черновика — нет: его никто не видит, а заполняют поездку в несколько
заходов (п. 7.1). Плюс кнопка «Обновить сайт» в панели рядом с индикатором.

Проверка: точка проверена на живом сайте (без входа 401, с токеном владельца
запускает сборку, повтор во время сборки — отказ, сразу после — отказ по интервалу);
панель — 21 проверка на подменённом воркере, через все состояния индикатора.

Критерии: А-08, А-09.

### Этап 2. Сообщество: роли, идеи и новая главная — третье демо

Этап добавлен в ТЗ v4 (`docs/TZ-nazarov-net-v4.md`) и поставлен вперёд по прямому
требованию заказчика. На ближайшем созвоне он хочет: заполнить поездку, дать
ссылку человеку, чтобы тот подписался по «+», и пройти путь организатора —
предложить свою поездку и получить доступ к ней в панели.

Порядок внутри этапа подчинён двум вещам: сначала то, что не ждёт чужих ключей,
затем роли (главное, что он хочет увидеть), затем остальное.

#### 2.1. Главная на букве S

Появляется: новый первый экран — баннер «A community, not a business. 100% free.
Forever.» со строкой «No fees · No subscriptions · No commissions», заголовок
«Sail. Ride. Jump. / Explore. Build. Together.», лента-S из пяти секций и блок из
четырёх призывов (Join the community, Suggest an idea, Join a trip, Build
together). Фотографии — собственные снимки заказчика из `public/assets/`. Плитки
«My interests» уступают место ленте; блок ближайших поездок с фильтром остаётся
ниже.

Подводные камни:

- Лента-S должна поместиться на экране телефона 390×844 — это требование
  заказчика, а не пожелание. Значит, секция не выше примерно 104 px, а название с
  золотой S не переносится на вторую строку. Замеряется и лента, и заголовок под
  ней: на 360×800 он вылезал за экран, когда секции были по 112 px.
- Буква S рисуется одной жирной SVG-линией **поверх фотографий**, а не лентой за
  секциями. Первый заход сделал наоборот — капсулы с обводкой и волосяная линия
  между ними, — и это провалилось: капсулы непрозрачные, линия показывалась
  только в зазорах, а пять обведённых пилюль в колонке читаются списком, что бы
  за ними ни лежало. Теперь обводок нет, линия пересекает снимки (как на
  макете), а текст лежит выше линии, чтобы она не шла сквозь слова.
- Картинка-подложка не подошла бы: направлений пять сейчас и шесть, как только
  заказчик добавит новое, а на картинке с пятью долями это была бы другая буква.
- Первая буква выделяется только у названия на S. Иначе добавленное направление
  «Hiking» получило бы золотую «H», которой в замысле нет.

Проверка: Playwright на 360 / 390 / 414 / 768 / 1024 / 1440 — лента целиком в окне
на телефонных ширинах, горизонтальной прокрутки нет; наведение на десктопе меняет
вид секции; нажатие в любое место секции ведёт на её вкладку.

Критерии: С-01, С-02, С-03.

#### 2.4. Админка на двух языках

Появляется: словарь подписей панели, переключатель EN / RU в боковом меню и на
экране входа, выбор запоминается в браузере. По умолчанию английский — как на
сайте.

Подводные камни:

- Переводится интерфейс, а не содержимое. Поля поездки по-прежнему заполняются на
  обоих языках независимо от языка панели, и это должно быть видно по подписям,
  иначе владелец решит, что переключатель меняет язык поездки.
- Переключателей на экране формы получается два, и выглядят они одинаково.
  Поэтому они разведены: язык панели — внизу бокового меню, рядом с аккаунтом;
  язык содержимого — над полями, и оба подписаны («Интерфейс», «Язык
  содержимого»). Без подписей первое же нажатие будет не тем.
- Строк много и они разбросаны по формам. Словарь делается типизированным, чтобы
  забытый ключ ловился `tsc`, а не глазами на демо.
- Сообщения об ошибках живут не в компонентах, а в `lib/` — в проверке поездки, в
  модулях Firebase, в сжатии картинок. Эти модули не знают, какой язык на экране,
  поэтому несут обе формулировки сразу (`Localized<string>`, базовый класс
  `LocalizedError`), а панель выбирает нужную.
- Выбор нельзя читать при первом рендере: страницы собраны заранее, и разметка
  разойдётся с тем, что гидратирует React. Нельзя и ставить состояние из эффекта
  — это каскадный рендер, который в проекте запрещён линтером. Остаётся
  `useSyncExternalStore`: React гидратирует по серверному снимку и сам переходит
  на сохранённый.

Проверка: обход всех экранов панели на обоих языках; перезагрузка сохраняет выбор;
`tsc` на полноте словарей.

Критерии: С-13.

#### 2.6. Организатор: доступ к своей поездке

Появляется: поле «Организатор» (почта) в форме поездки; регистрация и

- Право держится на подтверждённой почте в токене входа. Без проверки

организатора, регистрация с другого адреса (доступа нет), регистрация с нужного

### Этап 3. Письма, счётчики и списки

#### 3.1. «I'm interested» и счётчики Going / Interested

Появляется: кнопка и окно с одним полем email, текст «We'll email you when spots
open…», запись в Firestore и автоматическая подписка на интерес поездки; счётчики
на карточке и на странице поездки, аватарки до пяти и «+N more», порог показа из
настроек.

Подводный камень: счётчики читаются в браузере после загрузки, чтобы не устаревать
между сборками; до загрузки показывается то, что было на момент сборки, без скачка
вёрстки.

Что выяснилось при реализации. Живым читается только Interested. Going — это
занятые места или поправка владельца, то и другое меняется в админке, а значит
со сборкой; вторая его копия в базе умела бы только разойтись с первой, поэтому
её нет. `counters` — единственная коллекция, открытая на анонимное чтение, и
считает её воркер по записям в `interested`: счётчик, который мог бы написать
браузер, — это счётчик, в который кто угодно впишет что угодно. Читается он не
через SDK Firebase (сто килобайт ради одного числа), а одним `fetch` по REST,
и один раз на страницу: карточки в списке спрашивают одно и то же, первая
запускает запрос, остальные ждут его ответа. Аватарки — экипаж поездки из
справочника людей: это единственные фотографии людей, какие у сайта есть, а
имена тех, кто подал заявку, отданы владельцу, а не странице.

Проверка: нажатие увеличивает Interested и создаёт подписчика; ниже порога счётчики
скрыты; повторное нажатие с тем же email не удваивает число.

Критерии: П-13, П-14.

#### 3.2. Рассылка анонса подписчикам

Появляется: кнопка «Разослать подписчикам» у опубликованной поездки, предпросмотр
письма и число получателей, отправка только подписчикам этого интереса на их языке,
отметка «анонс отправлен» и отдельное подтверждение при повторной отправке.

Подводные камни:

- Отправка идёт из воркера порциями, с паузами, иначе EmailJS отобьёт по частоте.
  Прогресс виден в админке, и закрытая вкладка ничего не ломает.
- Лимит тарифа Personal — 2 000 писем в месяц, общий с ctmass.com. Перед отправкой
  показываем остаток и предупреждаем, если рассылка в него не помещается.

Что выяснилось при реализации. Рассылка уходит порциями по дюжине, и порции
гонит сама панель: у запроса воркера есть потолок исходящих обращений, а
каждое письмо — это отправка плюс запись о ней. Кому уже написали,
записывается в базу после каждого письма, поэтому закрытая вкладка рассылку
останавливает и больше ничего не делает: поездка открывается снова и
предлагает продолжить, а дважды не напишут никому. Отправка, которую не
принял EmailJS, тоже считается отправленной и попадает в список неудачных:
повторить её вслепую значит рискнуть вторым письмом тому, кто первое получил.

Остаток месячного лимита EmailJS по API не отдаёт, поэтому «показываем
остаток» выродилось в честное: сколько писем уйдёт сейчас, какой лимит у
тарифа и где смотреть остаток. Предупреждение появляется, когда одна рассылка
съедает больше половины месячного лимита.

Почтовый адрес отправителя обязателен по CAN-SPAM, и воркер отказывается
рассылать, пока его нет в настройках. Экран настроек — пункт 4.3, так что до
него рассылка заблокирована намеренно: это же не даёт отправить анонс раньше,
чем появится страница отписки из 3.3, ссылка на которую в письме уже стоит.

Проверка: два тестовых подписчика на разные интересы — анонс уходит одному; повторная
отправка требует подтверждения; письмо отображается оформленным, а не HTML-кодом.

Критерии: Н-07, Н-08, Н-11.

#### 3.3. Отписка и управление подпиской

Появляется: страница по ссылке из письма — отписаться целиком или снять отдельные
интересы, без пароля; ссылка «Unsubscribe» и почтовый адрес отправителя в каждом
письме; Privacy Policy на двух языках.

Подводный камень: ссылка должна открываться без входа, но не должна позволять
подобрать чужой адрес — используем длинный случайный ключ, а не email в адресе.

Что выяснилось при реализации. Отписка происходит только на POST. Ссылку в
письме открывают проверяльщики ссылок и почтовые сканеры, и страница, которая
действовала бы на открытие, отписывала бы людей, этой страницы не видевших;
поэтому `all=1` не отписывает, а ставит единственное нажатие впереди всего
остального — это те самые «один-два клика».

Адрес на странице показан замаскированным (`ma***@example.com`). Ключ
принадлежит человеку, но письма пересылают, и узнать свою подписку по такому
адресу можно, а собрать чужие — нет.

Снять все направления — это и есть отписка: подписка без единого направления
была бы подпиской ни на что. Сама отписка направлений не трогает, поэтому
«вернуться» возвращает ровно то, на что человек был подписан.

Приветственное письмо теперь тоже несёт ссылку отписки — раньше там стояла
фраза «ответьте на это письмо», которая и была заглушкой до этого пункта.

Privacy Policy осталась в пункте 5.2, где она и описана: политика должна
рассказывать и про пиксель Facebook с куками, а он появляется в 5.1. В подвале
пока только «Unsubscribe».

Проверка: отписка и последующая рассылка — письмо не приходит; снятие одного интереса
оставляет второй.

Критерии: Н-09, Н-10, Т-05.

#### 3.4. Админка: подписчики

Появляется: список подписчиков с интересами, языком, датой, источником и признаком
«через I'm interested»; количество по интересам; выгрузка CSV; удаление по просьбе.
Фильтр и отметка «обработано» у заявок Solutions.

Подводный камень: CSV должен открываться в Excel с кириллицей — пишем BOM и
разделитель, который Excel понимает.

Что выяснилось при реализации. Разделителя, верного везде, не существует: Excel
режет строку по разделителю списка своей локали — запятая в английской Windows,
точка с запятой в русской, и неверный складывает всю строку в одну колонку.
Поэтому файл следует языку панели: читающий панель по-русски почти наверняка
откроет файл в русском Excel. Google Таблицы распознают оба. BOM стоит всегда —
без него кириллица читается в ANSI и превращается в кракозябры.

Заявки Solutions перенесены в пункт 4.2. Их сейчас негде фильтровать: форма
отправляет письмо и нигде ничего не сохраняет, а сохранять их начинает как раз
4.2 («заявка приходит и в админку, и письмом»). Экран подписчиков об этом прямо
говорит, чтобы это не выглядело пропажей.

Удаление — это удаление записи, а не отметка. Отписка живёт в ссылке из письма и
запись сохраняет, чтобы человек мог вернуться к прежним направлениям; здесь же
выполняется другая просьба — «уберите мой адрес совсем», — которую флаг не
выполняет.

Проверка: выгруженный файл открывается в Excel и в Google Таблицах без иероглифов.

Критерии: А-16, А-17.

#### 4.2. Solutions

Появляется: страница `/solutions/` по содержанию п. 6.6 ТЗ — первый экран, четыре
услуги, «Our work» с проектами из админки, «How we work», форма заявки; управление
текстами и проектами в админке; письмо на support@ctmass.com.

Нынешняя страница IT Solutions заменяется, её адрес переадресуется (сделано в 1.8).
Запись через Calendly уже стоит на ней с пункта 2.9.

Проверка: заявка приходит и в админку, и письмом; проект добавляется и сортируется
из админки.

Критерии: П-17, А-18.

Что выяснилось при реализации. Прежняя страница IT Solutions продавала «целую
IT-команду» девятью блоками — первый экран, «о нас», принципы, кейсы, услуги,
процесс, промо поездки, FAQ и форма. По §6.6 вкладка короче и конкретнее:
что делаем, что уже сделали, как идёт работа, форма. Старые блоки и их тексты
удалены вместе с разделом it в словарях — страницы, которую они описывали,
больше нет. Английский в новом тексте взят из §6.6 дословно: по нему
принимают работу, и пересказ своими словами развёл бы страницу и ТЗ.

Форма перестала отправлять письмо из браузера и ушла на /api/solutions. §6.6
требует, чтобы заявка сохранялась в админке, а коллекция solutionsInquiries
закрыта для браузеров: в ней имя, адрес и телефон каждого, кто просил смету.
Порядок внутри — сначала запись, потом письма: упавшее письмо нельзя
показывать как упавшую заявку, иначе её отправят второй раз и один проект
посчитают дважды.

Вместе с этой формой из сайта исчез последний отправитель писем на стороне
страницы, а с ним и пакет @emailjs/browser. Теперь все письма уходят из
воркера приватным ключом — то, что в DEPLOY.md было оговоркой «кроме формы
Solutions», стало правилом без исключений.

Четыре варианта в вопросе «что нужно» живут в lib/content/solutions.ts, а не
в текстах страницы: те же четыре слова нужны форме, письму в студию и списку
в панели, а два из трёх работают в воркере, который собирает wrangler и
который про алиасы Next ничего не знает. Храним id, показываем подпись:
переименовать подпись — это перевод, переименовать id — осиротить все
сохранённые заявки.

Тексты и услуги настраиваются по-разному, и это осознанно. Заголовок с
подзаголовком — по полю и по языку, как везде. Список услуг и список шагов —
целиком: собрать карточку наполовину из ТЗ, наполовину из настроек — значит
описать услугу, которой нет. Пустой список, а он пустой у неоткрытых
настроек, означает «как в §6.6».

«Our work» — отдельная коллекция, но редактируется на экране настроек и
сохраняется его же кнопкой. Для владельца это три строки страницы услуг,
и §7.7 перечисляет их там же; отдельный пункт меню ради трёх карточек —
лишний пункт меню. Порядок — это позиция в списке: стрелки те же, что у
остальных повторяемых блоков, и страница печатает карточки ровно так, как
они стоят в форме. Пока своего проекта нет, блок показывает nazarov.net и
ctmass.com из §6.6 — страница, которая продаёт работу, не может говорить
«работ пока нет», а примеры исчезают с появлением первого настоящего
проекта.

Заявки Solutions встали рядом с заявками на поездки, под тем же пунктом
меню: §7.6 — это один раздел с двумя видами просьб, и работают с ними
одинаково — прочитать, ответить, отметить сделанным. Переключатель видит
только владелец: заявка на разработку сайта к поездке организатора
отношения не имеет. Панель меняет в заявке единственное поле — «обработано»;
остальное — то, что человек прислал, и запись, которую можно править,
перестаёт быть доказательством того, о чём просили.

#### 4.3. Настройки в админке

Появляется: раздел «Настройки» — тексты Story и Solutions, тексты About и баннера
сообщества, адрес Calendly, пороги показа счётчиков, почтовый адрес отправителя,
ID канала и плейлистов YouTube.

Подводный камень: тексты About и первого экрана главной до этого живут в коде.
Перенос должен оставить нынешние значения значениями по умолчанию, иначе первая же
пустая настройка сотрёт готовую страницу.

Что выяснилось при реализации. Правило «пусто — значит оставить как есть»
действует по каждому полю и по каждому языку отдельно: текст живёт в коде, а
настройки его перекрывают, и первое сохранение с сорока незаполненными полями
не меняет ничего. Русская правка при этом не утаскивает за собой английскую
фразу, потому что владелец правит панель в одном языке за раз.

About отдан в настройки не целиком: только начало и концовка. Середина — это
концепция сообщества (ТЗ v4, §5), документ, который согласуют целиком, а не
копия, которую переписывают; форма из шестидесяти вложенных полей — это форма,
которую никто не открывает. Экран прямо об этом говорит.

Слова первого экрана главной уехали из компонента в отдельный модуль
(components/home/home-copy.ts): иначе резолвер настроек не мог бы взять
значения по умолчанию, не втащив за собой весь компонент.

На экране настроек пустое поле — нормальный ответ, поэтому подпись «не
заполнено» на второй язык там выключена: страница в янтарных предупреждениях
врала бы о состоянии дел. В форме поездки, где заполнить обязаны оба языка,
подпись осталась.

Почтовый адрес отправителя теперь есть где заполнить — это снимает запрет на
рассылку анонса из пункта 3.2.

Проверка: правка текста в панели меняет страницу после пересборки; пустое поле
возвращает значение по умолчанию, а не пустоту.

Критерии: А-15, А-18.

### Этап 5. Реклама, поисковики, качество, сдача

#### 5.1. Пиксель Facebook, серверные события, баннер cookies

Требует созданного пикселя и токена (раздел 4).

Делается после 5.2, и это не перестановка ради удобства: баннер согласия
обязан вести на политику конфиденциальности, а политика появляется в 5.2.
Ссылка на страницу, которой ещё нет, — это 404 в самом заметном месте сайта.

Появляется: баннер согласия в стиле сайта; пиксель подключается только после согласия;
события «Подписка», «Interested», «Заявка», «Заявка Solutions» в браузере и дублем
через `/api/capi` с единым идентификатором события, чтобы Facebook отсеял повторы.

Проверка: до согласия во вкладке «Сеть» нет запросов к facebook.com; события видны в
Events Manager и в Meta Pixel Helper.

Критерии: П-20, Ш-06.

Что выяснилось при реализации. Пикселя и токена пока нет, и это не помешало:
всё написано так, что без id пикселя Facebook на сайте нет вообще — ни
скрипта, ни cookie, ни баннера. Баннер, спрашивающий разрешение на то, чего
не происходит, — единственный баннер хуже отсутствующего. Когда заказчик
создаст пиксель, включается всё сразу, двумя значениями: id переменной сборки
и токен секретом воркера.

Согласие — это три состояния, а не два: не ответил, да, нет. «Не ответил»
обязано вести себя точно как «нет», потому что П-20 проверяется первым
открытием сайта с вкладкой «Сеть», и честный способ это пройти — чтобы
скрипта ещё не существовало. Загрузку пикселя поэтому вызывает одно место —
баннер, и только по ответу «да».

У хранения согласия появилось четвёртое значение — «ещё не смотрели».
Страницы печатаются на сборке, а localStorage читается только после
гидратации; снимок «не ответил» для сервера означал бы, что баннер
впечатывается в html каждой страницы и тут же исчезает у того, кто ответил
месяц назад. Отдельное значение рисует пустоту, а настоящий ответ приезжает
тиком позже.

Событие уходит дважды с одним eventId, и id — не украшение: без него
подписка, дошедшая по двум каналам, посчитается дважды, а цена подписчика в
отчёте окажется вдвое меньше настоящей. Facebook отбрасывает вторую копию
сам.

Имена событий — стандартные там, где они есть, и своё там, где нет.
«Interested» в номенклатуре Facebook отсутствует, и подогнать его под Lead
значило бы слить в отчёте с заявкой — то есть с тем, чего он нарочно дешевле.
Повторное нажатие событием не считается: воркер возвращает created / counted,
и только новая подписка и новый интерес отчитываются как конверсия.

Адрес почты хешируется в воркере, а не в странице. Страница не может
доказать, что сделала это, а адрес, пришедший в открытом виде, пересылать
нельзя — так что sha256 считается на сервере, и наружу уходит только он.

Баннер пришлось сузить: на 360px первая версия занимала 424px — половину
экрана под вопросом. Текст короче, кнопки в один ряд, шрифт на телефоне
меньше; стало 356px. Подробности — на странице политики, куда баннер и
ведёт.

#### 5.2. Поисковики, Privacy Policy, 404

Появляется: карта сайта с опубликованными поездками и без архивных, разметка языковых
версий, заголовки страниц, страница Privacy Policy на двух языках, страница 404 в стиле
сайта, почтовый адрес отправителя в настройках.

Проверка: `sitemap.xml` открывается и не содержит черновиков и архива; переадресация
http на https; hreflang на пяти страницах.

Критерии: Т-03, Т-05, Т-06.

Что выяснилось при реализации. Карта сайта строится из того же чтения базы,
из которого строятся страницы, поэтому черновик и архив в неё не попадают не
по фильтру, а по устройству: `getSiteContent` их не возвращает, и до этого
файла им не доехать. Проверка сверяет число адресов поездок с числом
опубликованных поездок в базе — лишняя запись сразу ломает равенство.

Страницы отписки в карте нет, и это то же решение, что `noindex` на ней
самой: это страница про чью-то одну подписку, а поисковик, прошедший по
ключу из пересланного письма, — единственный посетитель, которого там быть
не должно. Панели нет по той же причине, только проще: индексировать форму
входа незачем.

Метаданные страницы и карта сайта говорят про языки одно и то же, нарочно
дважды. У страниц hreflang уже был (`alternates.languages` в
`buildMetadata`); в карте он закрывает страницы поездок, которых в карте
может быть сколько угодно, не заставляя поисковик сперва их обойти. Next,
кстати, печатает атрибут как `hrefLang` — в HTML регистр имени атрибута не
важен, так что это вопрос вида, а не работы; проверка ищет без учёта
регистра.

Политика написана от того, что сайт действительно делает, а не по шаблону:
перечислены ровно те шесть служб, с которыми он разговаривает (Firebase,
Cloudflare, EmailJS, YouTube, Calendly, Meta), и ровно те поля, которые
спрашивают формы. Почтовый адрес берётся из настроек — то же поле, что в
письмах; пока он пуст, блока нет, потому что адрес, по которому нельзя
написать, хуже, чем адрес почты над ним.

**Переадресация http → https на боевом домене не работала.** Проверка
`curl -I http://nazarov.net/` отвечала 200, а не 301: HTTPS включён, но
незащищённый вход тоже открыт. Кодом это не лечится — страницы отдаёт сам
Cloudflare, воркер их не видит (`run_worker_first` перечисляет только
`/api/*`). Это переключатель в кабинете: SSL/TLS → Edge Certificates →
Always Use HTTPS. Шаги — в DEPLOY.md §8.

Страница 404 была ещё с лендинга — «Back to AI Yacht». Теперь она про
нынешний сайт и ведёт не только на обе главные, но и на четыре направления:
кто промахнулся адресом поездки, чаще всего искал поездку, а не главную.
Направления в ней записаны прямо, без чтения базы: это одна статическая

#### 5.3. Резервные копии данных

Появляется: выгрузка Firestore по расписанию, проверенное восстановление, описание
процедуры в README.

Проверка: восстановление из выгрузки в тестовый проект.

Критерии: Т-04.

Что выяснилось при реализации. Штатная выгрузка Firestore по расписанию
требует тарифа Blaze, своего бакета и пишет формат, который читает обратно
только Google. В базе несколько сотен документов, поэтому выгрузка — это два
скрипта и папка JSON: `scripts/firestore-backup.mjs` и
`scripts/firestore-restore.mjs`. Коллекции скрипт спрашивает у базы, а не
перечисляет сам, иначе коллекция, добавленная позже, тихо не попадала бы в
копию.

Документы сохраняются в родном виде Firestore (`{"seats":{"integerValue":"8"}}`),
а не в «удобном». Копия нужна, чтобы её восстановить, и родной вид — это то,
что `:commit` принимает обратно, не заставляя угадывать, было число целым
или дробным.

Восстановление по умолчанию ничего не пишет. Это единственная операция,
которая способна разрушить больше, чем починить, — она перекрывает живые
документы старыми копиями, — поэтому безопасное поведение сделано
поведением по умолчанию, а опасное надо набрать руками: `--force` плюс
`--project`. Без названного проекта `--force` отказывает: смысл репетиции в
том, чтобы восстанавливать в тестовый проект, а значение по умолчанию «живой»
превращает репетицию в происшествие. Пишет с маской полей и слиянием —
документ, которого в копии нет, остаётся, и поле, добавленное после снимка,
не удаляется.

Фотографии не копируются, и это записано в самом манифесте. Они лежат в
Cloud Storage со своей надёжностью, а их адреса — внутри документов, которые
копия как раз содержит: потерянный бакет — это известный список файлов, а не
загадка.

**Ночное расписание я не добавлял.** Выгрузка по cron означает, что база —
вместе с адресами людей и тем, что они о себе написали, — каждую ночь
уезжает в хранилище артефактов GitHub. Это решение о персональных данных, а
не технический шаг, поэтому оно за заказчиком: готовый файл workflow лежит в
DEPLOY.md §11 текстом, вместе с шагами по секрету `FIREBASE_SERVICE_ACCOUNT`
и с альтернативой — запускать выгрузку руками перед рискованным, то есть
тогда, когда копия действительно нужна.

Папка `backup/` добавлена в `.gitignore`: копии с персональными данными не
место в репозитории.

Проверка восстановления в настоящий тестовый проект — за заказчиком (нужен
второй проект Firebase и его ключ); шаги расписаны в DEPLOY.md §11. Логику
обоих скриптов проверяет `backup-test.mjs` на подменённой сети: 23 проверки,
включая постраничное дочитывание, состав файлов, манифест, отказ `--force`
без проекта и маску полей при записи.

#### 5.4. Сквозное тестирование

Появляется: полный набор проверок Playwright по всем критериям раздела 15 ТЗ и
раздела 14 ТЗ v4, отчёт Lighthouse для главной, вкладки и страницы поездки, проверка
в Chrome, Safari, Firefox, Edge, прохождение сценария п. 7.1 ТЗ с телефона.

Критерии: Т-01, Т-02, А-19 и повторная проверка всех предыдущих.

Что выяснилось при реализации. Проверки собраны в репозитории, в папке
`tests/`, и запускаются одной командой: `npm test`. Playwright используется
напрямую, без его тест-раннера, — раннер добавил бы файл конфигурации,
репортер и модель воркеров ради двух сотен утверждений по статической
выгрузке, а так одни и те же файлы ходят и по `out/`, и по живому сайту с
одним флагом `--site`.

Каждая проверка подписана кодом критерия. Отчёт печатает таблицу «по
критериям», поэтому его читают против раздела 15 ТЗ и раздела 14 ТЗ v4, а не
против имён функций. Критерий, который браузер решить не может, объявлен
непроверяемым вместе с причиной и печатается отдельным списком — пробел в
проверке виден, а не замаскирован.

Наборов пять: `public` (меню, главная, направления, два языка, ширины от
320 px, политика, карта сайта, 404), `trip` (страница поездки, «Поделиться»,
превью), `forms` (подписка, заявка, идея, Solutions, отписка), `platform`
(каждая страница в каждом движке) и `admin`. Во всех четырёх движках гоняется
только `platform`: остальные в каждом браузере дали бы тот же ответ вчетверо
дольше. Т-02 закрыт — Chrome, Firefox, Safari (WebKit) и Edge проходят все
страницы без ошибок в консоли, с работающим фильтром, диалогом подписки и
меню на телефоне.

Turnstile подменяется. Он отказывает автоматизированному браузеру — так
задумано, и уговорить его нельзя, — а без подмены каждая форма навсегда
стоит на «проверяем, что вы человек». Проверяется форма, а не Cloudflare:
настоящий виджет проходит человек, а серверная половина — отказ запросу без
токена — живёт в воркере.

Формы никуда не отправляются: каждая точка `/api/…` отвечает прямо в
браузере. Так видно две вещи, которых не покажет настоящая отправка, — что
именно страница посылает (где и обнаруживается лишнее или потерянное поле) и
что она показывает в ответ, — и боевая база остаётся нетронутой.

Админский набор пишет в настоящую базу и убирает за собой. Всё, что он
создаёт, — черновик: посетителю он не виден и пересборку не запускает, потому
что `rebuildAfterTrip` запускает её только для поездки, которая опубликована
или была опубликована. Набор проходит весь сценарий п. 7.1 — создать,
заполнить два языка, расписать дни, переставить и удалить день, посмотреть
предпросмотр, в архив и обратно, дублировать, удалить с подтверждением — и
заканчивает проверкой, что ни одной проверочной поездки не осталось.
Публикацию и рассылку он не делает: обе видны настоящим людям, одна кладёт
тестовую поездку на живой сайт, другая шлёт письма.

П-06 иначе и не показать: у всех живых поездок блоки заполнены, поэтому
«незаполненный блок не выводится» проверяется на черновике, который нарочно
наполовину пуст, — сначала предпросмотр без блока «День за днём», потом, с
добавленными днями, с ним.

Что нашлось и было исправлено по ходу: у форм не было ссылки на политику
конфиденциальности. Текст согласия был у всех четырёх, а самой политики
тогда ещё не существовало — она появилась только в 5.2. Теперь согласие
выводит общий `FormConsent`, и все четыре формы ведут на одну политику
(Т-05).

Код выхода `npm test` — число непрошедших проверок, так что команда годится и
для CI. Что именно проверяет человек и почему — таблицей в `tests/README.md`.

**Т-01 сначала не выполнялся, и это заняло четыре круга.** Медиана трёх
прогонов Lighthouse по боевому сайту, мобильный профиль: главная 80, раздел
81, страница поездки 79 при пороге 85. Доступность 95–98, SEO 100, практики
100 — там вопросов не было ни разу.

*Первое.* На странице поездки Turnstile грузился при загрузке — около 1,7 МБ
и почти четыре секунды возни с сетью и основным потоком, — хотя форма,
которую он охраняет, в самом низу. LCP от этого уезжал на пятнадцать секунд.
Теперь виджет запрашивается по одному из двух событий, что случится раньше:
он подошёл на половину экрана к области видимости или посетитель впервые
коснулся формы. Второе важно потому, что Enter в текстовом поле отправляет
форму, а запрос без токена воркер отклоняет, — до кнопки нельзя добраться
раньше, чем проверка начнёт загружаться. Там, где форма и так на первом
экране (`/suggest/`, `/solutions/`, диалог подписки), наблюдатель срабатывает
сразу и ничего не меняется.

*Второе.* У главной LCP — первая фотография ленты-S, и она была
`loading="lazy"`. Браузер не запрашивает ленивую картинку, пока не разложит
страницу, и это давало лишнюю секунду задержки до запроса. Первая картинка
ленты теперь `eager` с `fetchpriority="high"`, остальные остались ленивыми.

*Третье — главное.* Сайт отдаётся статической выгрузкой, оптимизатора
картинок Next в ней нет, и файл из репозитория телефон скачивает как есть:
фотография шириной 1920 в рамке шириной 480 — это вчетверо больше байтов без
разницы на глаз. На главной таких байтов был килобайт: 1022 КБ, то есть пять
секунд на throttled-соединении Lighthouse. Появились
`scripts/image-variants.mjs` (WebP-копии в 480, 960 и 1440 пикселей плюс
манифест) и компонент `<Photo>`, который отдаёт их через `srcset`, оставляя
исходный JPEG в `src` как запасной вариант. `sizes` у `<Photo>` обязателен по
типу: без него браузер считает, что картинка во всю ширину окна, и берёт
самую большую копию — ровно то, против чего всё затевалось. Главная на
десктопе грузит 69 КБ картинок вместо 1022, на телефоне — 12 КБ. Попутно
девять фотографий в `public/assets` были выгружены почти без сжатия
(`yasha.jpg` — 695 КБ при 912×904); перекодированы, папка с 6,4 МБ ушла до
3,9.

*Четвёртое.* Счётчики «едут» и «интересно» запрашивались во время гидратации,
хотя числа на странице уже напечатаны сборкой. Запрос обновляет то, что
посетитель и так читает, — теперь он ждёт простоя браузера
(`requestIdleCallback` с таймаутом 2,5 с) и идёт с низким приоритетом. Это
дало больше всех: главная 86 → 95, раздел 86 → 96.

**Итог — медиана пяти прогонов по боевому сайту:** главная 95, раздел 96,
страница поездки 86. Доступность 95–98, SEO 100, практики 100.

**Про сами измерения.** Один прогон Lighthouse — не число. Три прогона одной
и той же страницы дали здесь 98, 86 и 79 при одинаковых сетевых таймингах:
картинка каждый раз приходила за 150 мс, а отрисовка ждала основной поток то
115 мс, то 2013. Lighthouse замедляет процессор в фиксированное число раз,
поэтому всё, чем машина занята ещё, ложится прямо в результат. Отсюда
`--runs N` с медианой и `--psi`, который спрашивает PageSpeed Insights — тот
же Lighthouse на серверах Google. Квота без ключа общая на всю сеть и
кончилась на первом же запросе; бесплатный ключ передаётся в `PSI_KEY`, и
окончательное слово по Т-01 стоит оставить за ним или за
pagespeed.web.dev.

Отчёты снимаются по боевому сайту, а не по локальной сборке: ту отдаёт
маленький node-сервер по http, без сжатия, заголовков кэша и CDN, и её числа
ничего не говорят о том, что получает посетитель.

**Добавлен набор `links` — весь сайт одним обходом.** Остальные наборы знают
по горсти адресов; этот не знает ни одного. Он начинает с двух главных и с
`sitemap.xml`, идёт по всем ссылкам внутри сайта и спрашивает каждый файл, на
который страницы ссылаются: 38 страниц и 78 файлов на боевом сайте за один
проход. Проверяет, что ссылки ведут на существующие страницы, что все
картинки на месте, что внутри сайта нет ссылок по http, что `canonical`
указывает на саму страницу, что у каждой страницы есть пара на другом языке и
она открывается, что у каждой есть своя картинка и описание для превью и что
карта сайта и страницы совпадают в обе стороны. Страницы с `noindex`
(`/unsubscribe/`) из «поисковой» половины проверок исключены: у них нет ни
canonical, ни пары языков, ни превью — и правильно, что нет.

Нашёл настоящую поломку. **Восемь из тридцати шести адресов в `sitemap.xml`
отвечали 404.** Четыре направления, которые существуют только как категории
формы идей — Family Travel, Hiking & Camping, Road Trips, Other Adventures, —
скрыты со сайта (признак `hidden`), поэтому страницы вкладок для них не
собираются вовсе. А `sitemap.ts` перечислял все направления подряд, и обе
языковые версии каждого скрытого попадали в карту. Для Google это
«Submitted URL not found (404)» по восьми адресам сразу. Исправлено одной
строкой — карта берёт `visibleInterests(interests)`, — и в новой сборке 28
адресов, все живые. Поездки скрытого направления адрес сохраняют: `hidden`
прячет вкладку, не трогая поездки (§7.3), так что из карты они не уходят.

#### 6.3. Направления: Sidekicks, Summits, Something Else

Главная теперь: Sailing, Snowboarding, Sidekicks, Summits, Skydiving,
Something Else, Software — все семь на S, ради чего буква и рисуется.

Son стал Sidekicks и поднялся на третье место. Hiking & Camping стал Summits,
вышел из скрытых и получил вкладку. Skydiving переехал за Summits и описан как
экстремальное направление — прежний текст про первый прыжок в тандеме
противоречил «по приглашению или с требованием к опыту». Other Adventures стал
Something Else. Family Travel и Road Trips убраны из формы идей: первое
слилось с Sidekicks, второе заказчик вычеркнул. Записи их остались — на них
могут ссылаться уже присланные идеи.

Something Else ведёт с главной на форму идей, а не на свою вкладку: у него нет
страницы и нет места в меню, но на главной оно просится. Правило в коде
привязано к флагу «спрашивать свою категорию», а не к слагу, так что имя,
подпись и фотография остаются редактируемыми из панели.

`/son/` был живым и проиндексированным, поэтому 301 на `/sidekicks/` в обоих
языках. У двух других направлений страниц никогда не было.

У страницы направления без обложки появилось превью по умолчанию: вкладка
живёт с момента сохранения, а фотографию грузят после.

Обложки Summits и Something Else поставлены 25.11.2026: своих фотографий этих
направлений пока нет, поэтому взяты два снимка в общественном достоянии —
походная тропа и костёр в лагере, оба съёмки государственных служб США.
Откуда они и почему их можно использовать — `docs/photo-credits.md`. Заменить
своими — одна операция в панели, и файл из репозитория после этого удаляется.

#### 6.4. Календарь всех мероприятий — `/calendar/`

Новая страница в обоих языках: все опубликованные поездки по датам, сетка
месяца и список поездок этого месяца рядом. Сетка отвечает на «как выглядит
февраль», список — «что это, собственно»; на телефоне одна сетка была бы
стеной цветных квадратов, где в клетку шириной сорок пикселей не влезает
название.

Открывается на месяце ближайшей незавершённой поездки, а не на текущем:
поездок четыре-пять в год, и пустая сетка выглядела бы как календарь, в
котором ничего нет. Стрелки упираются в первый и последний месяц, где
что-то есть. Всё содержимое уже в странице, так что переключение месяцев
мгновенное и ничего не грузит.

Неделя начинается с воскресенья по-английски и с понедельника по-русски. Даты
считаются в UTC от начала и до конца: день поездки — это календарный день, а
не момент, и браузер западнее Гринвича превратил бы «2027-05-08» в седьмое.

Ссылки на календарь: подвал, меню-гамбургер и блок «Ближайшие поездки» на
главной. В верхнем ряду на десктопе его нет — ряд уже занят направлениями
(см. 6.3). Если захочется и там, придётся убрать что-то другое.

#### 6.5. Верхняя панель — шире и без тесноты (25.11.2026)

Заказчик сказал: на десктопе всё прижимается. Так и было, причём в двух
местах сразу.

Ряд получил собственную ширину — 90rem вместо 72rem, которыми ограничена
колонка страницы. Колонка узкая потому, что строку текста шире 72rem тяжело
читать; у ряда ссылок такой проблемы нет, и каждый пиксель, отданный ему, —
пиксель, за который ссылки не дерутся. На 72rem в 1112 пикселях помещались
пять направлений, пять страниц, панель и переключатель языка — и оставалось
четыре пикселя: одно слово, и переключатель уехал бы за край экрана.

Ряд появляется целиком или не появляется вовсе, с 1200 px. Целиком — потому
что панель, которая показывает страницы и прячет направления, оставляет
посетителя вообще без пути к направлению: бургер к этой ширине уже скрыт.
Именно это делала предыдущая редакция между 1024 и 1280 — ошибка, найденная
этой же проверкой. А 1200 — потому что там ряд действительно помещается, и
это измерено на 21 ширине от 320 до 2560 в обоих языках, а не угадано. Число
задаёт русский: «Предложить приключение» и «Панель» длиннее английских, а
порог один на оба.

Зазоры растут вместе с окном — 12 px там, где тесно, 16 на 1280, 20 на 1536 —
вместо того чтобы ряд менял состав. Надпись «My interests» убрана совсем, и
на её место с 1440 px встал «Календарь»: надпись называла соседние ссылки, а
эта ведёт на страницу. Уже 1440 календарь есть в подвале каждой страницы и в
блоке ближайших поездок на главной, ещё уже — в меню со всем остальным.

Заодно нашлось, что ссылка на календарь доходила только до самой страницы
календаря: `calendarHref` прокидывался в один вид из десяти. Теперь во все.

Проверено измерением на каждой ширине и на трёх страницах: ничего не вылезает
за край, ничего не переносится на вторую строку, высота панели не меняется, а
в самом тесном месте (русский на 1200 px) между ссылками и переключателем
языка 24 px воздуха.

**Проверено (6.1–6.4):** `tsc`, `lint`, сборка; `npm test` — 163 проверки,
0 падений; форма идей проверена в браузере от начала до конца (карта
открылась, поиск нашёл место, «взять это место» заполнило поле и координаты,
отправка ушла с `€1 500` и парой дат); загрузка фотографии дошла до Storage по
верному пути и получила ожидаемый отказ (правила ещё не опубликованы); меню не
вылезает за край на 1024, 1280, 1440 и 1920.

## 6. Реестр рисков

| Риск | Чем грозит | Что делаем |
| --- | --- | --- |
| Firebase Storage требует Blaze с картой | нельзя грузить фото | проверяем в пункте 0.3; запасной путь — стороннее бесплатное хранилище картинок |
| Доступ к EmailJS не получен | письма из пунктов 2.5–2.8 не уходят | точки работают без писем и говорят об этом в ответе; отправка включается секретом |
| Лимит EmailJS 2 000 писем в месяц общий с ctmass.com | рассылка обрывается на середине | остаток показывается перед отправкой, отправка порциями и возобновляемая |
| Полный почтовый адрес не предоставлен | нарушение CAN-SPAM | адрес — поле настроек, рассылка блокируется, пока оно пустое |
| Пересборка при публикации | заказчик ждёт до 5 минут | предпросмотр в админке мгновенный, индикатор сборки в админке |
| Много фото у поездки | медленная страница | сжатие перед загрузкой, подгрузка по мере прокрутки |
| Спам в формах | мусор в базе и расход писем | Turnstile проверяется на сервере, запись в Firestore из браузера закрыта |
| Организатор получает доступ по почте | чужой человек заберёт чужую поездку | доступ только при подтверждённой почте; проверяет правило Firestore, не интерфейс |
| Лента-S не влезает в телефон | главная выглядит сломанной там, где её чаще всего и смотрят | высота секции задана сверху, ширины 360 / 390 / 414 проверяются замером на каждой правке |
| Рост числа поездок | долгая сборка | перечень путей строится одним запросом, картинки соцсетей кэшируются |

## 7. Что в этой реализации не делаем

По разделу 12 ТЗ и по прямому решению заказчика:

- онлайн-оплата Stripe, waiver, статус «Paid» — этап 2;
- личные кабинеты участников: регистрация Member, профиль, избранное, история
  поездок. Member в v4 — это заявка, а не аккаунт (ТЗ v4, п. 2.2);
- роль Community Contributor — сам источник называет её необязательной;
- комментарии и отзывы;
- мобильное приложение, CRM, Telegram-бот, push-уведомления;
- перевод рассылки на почтовый сервис;
- написание и перевод текстов, фото- и видеосъёмка;
- ведение рекламы в Facebook;
- пункт 5.5 целиком — иллюстрированная инструкция, список доступов и
  обучающая сессия с записью (решение заказчика от 21.11.2026: инструкцией
  пользоваться не будут). Критерии О-01, О-02, О-03 снимаются; что осталось
  вместо них — в самом пункте 5.5;
- пиксель Facebook включается, но не включён: код из пункта 5.1 на сайте,
  id пикселя не заведён, поэтому Facebook не загружается вообще и баннера
  cookies нет. Ш-06 проверяется, когда заказчик захочет рекламу.
