**Источник требований:** `docs/TZ-nazarov-net-v3.docx` (версия 3.0 от 27.09.2026).
`docs/TZ-nazarov-net.md` (версия 2.0) оставлен как история — расхождения разобраны в разделе 2.

**Исключено по решению заказчика:** онлайн-оплата Stripe (депозит, payment links, waiver).

дизайне (это показываем заказчику первым), затем подписки, письма и YouTube.

## 1. Как мы работаем

Один пункт плана = работа в ветке `dev` = коммит = pull request `dev → main` = merge
commit. Следующий пункт начинается только после того, как предыдущий влит.

Каждый пункт закрывается по одному и тому же шлюзу проверки. Пункт не считается
сделанным, пока весь шлюз не зелёный:

| Проверка | Команда | Что ловит |
| --- | --- | --- |
| Типы | `npx tsc --noEmit` | ошибки типов, несобранные пропсы, забытые ключи словарей |
| Линт | `npm run lint` | неиспользуемое, правила Next.js |
| Сборка | `npm run build` | падения статического экспорта, ошибки пререндера |
| Вывод сборки | поиск по `out/` | что нужные страницы реально появились, а черновики — нет |
| Сценарий | Playwright по `out/` через локальный статический сервер | что страница работает в браузере, без ошибок консоли |
| Вёрстка | Playwright: ширины 320 / 360 / 390 / 768 / 1024 / 1440 | горизонтальная прокрутка и «поехавшие» блоки |

Playwright уже установлен локально (`node_modules/playwright`), импорт —
`file:///F:/Yacht/node_modules/playwright/index.mjs`. Проверять сборку `out/` нужно
маленьким статическим сервером, а не `next dev`: HMR-вебсокет дев-сервера подвешивает
закрытие контекста Playwright.

Деплой на боевой nazarov.net запускает George вручную через GitHub Action
«Deploy to Cloudflare». Сами мы не деплоим ничего.

## 3. Архитектура: принятые решения и почему

### 3.1. Сайт остаётся статическим, данные приезжают на сборке

`next build` с `output: "export"` читает Firestore и печатает готовый HTML для каждой
опубликованной поездки. Это даёт быстрые страницы, работающие превью ссылок в соцсетях
и нормальную индексацию — то, ради чего в ТЗ стоят критерии Т-01, Ш-03, Ш-05.

Следствие, с которым живём осознанно: между «Опубликовать» в админке и появлением
страницы на сайте проходит время пересборки. В ТЗ это зафиксировано как 5 минут
(критерии А-08, А-09).

Что этому не мешает:

- **Предпросмотр** (А-07) рисуется в админке теми же React-компонентами из черновика,
  без всякой пересборки. Заказчик видит результат сразу.
- **Счётчики Going / Interested** подтягиваются в браузере после загрузки страницы,
  поэтому не устаревают между сборками.
- **Переход Upcoming в Past** обеспечивается ежедневной пересборкой по расписанию
  (cron в GitHub Actions), как и записано в Приложении А ТЗ.

### 3.2. Серверные точки входа — на Cloudflare Worker, не на Firebase Functions

Сейчас Cloudflare отдаёт только статику (в `wrangler.jsonc` нет `main`). Добавляем
воркер-скрипт: статика по-прежнему отдаётся напрямую с edge и воркер для неё не
запускается, а воркер обрабатывает только `/api/*`.

Зачем это нужно:

| Точка входа | Зачем |
| --- | --- |
| `/api/subscribe` | проверить Turnstile и записать подписчика, не открывая Firestore на запись всему интернету |
| `/api/interested` | то же для кнопки «I'm interested» |
| `/api/application` | заявка на поездку |
| `/api/solutions` | заявка Solutions |
| `/api/rebuild` | по кнопке «Опубликовать» дёрнуть GitHub Action пересборки, храня токен в секрете воркера |
| `/api/capi` | серверные события Facebook (Conversions API) |

Почему не Firebase Cloud Functions: они требуют тарифа Blaze с картой. Cloudflare
Workers на бесплатном тарифе дают 100 000 запросов в сутки, и запросы к статике в этот
лимит не попадают. Дополнительных расходов не возникает — Приложение Б ТЗ не меняется.

Воркер ходит в Firestore по REST API от имени сервисного аккаунта (JWT подписывается
Web Crypto прямо в воркере). Благодаря этому правила Firestore закрывают запись из
браузера полностью.

### 3.3. Права доступа к Firestore

| Кто | Что читает | Что пишет |
| --- | --- | --- |
| Аноним: сайт и сборка | опубликованные поездки, интересы, люди, настройки, проекты Our work, счётчики | ничего |
| Владелец: вошёл в админку | всё | всё |
| Воркер: сервисный аккаунт | всё | подписчиков, заявки, счётчики |

Подписчики и заявки не читаются анонимно никогда — иначе чужая база email утекает
одной строкой в консоли браузера.

### 3.4. Админка на статическом экспорте

Адрес один: `/admin/`. Внутренняя навигация — через строку запроса
(`/admin/?view=trips&id=...`). Так перезагрузка страницы и сохранённая ссылка работают:
Cloudflare всегда отдаёт `out/admin/index.html`, а строка запроса на выбор файла не
влияет. Вложенные адреса вида `/admin/trips/abc` на статике дали бы 404.

Админка целиком клиентская, в сборку сайта её данные не попадают. `useSearchParams`
в статически отрендеренном маршруте требует обёртки `<Suspense>` — учтено.

### 3.5. Один рендерер поездки на три места

Компоненты страницы поездки принимают на вход объект `Trip` и используются:

1. на публичной статической странице `/sailing/<slug>/`;
2. в предпросмотре админки;
3. при генерации картинки для соцсетей.

Правило «незаполненный блок не показывается» (П-10) живёт внутри рендерера, а не в
трёх копиях.

### 3.6. Что делаем с нынешним лендингом AI Yacht

Его разметка и словари — это и есть образец страницы поездки. По пунктам 1.4 и 1.6
компоненты `hero`, `price`, `program`, `route`, `team`, `faq`, `apply` переезжают
с «текста из словаря» на «текст из объекта Trip». По пункту 1.11 сама поездка AI Yacht
заводится через админку и сверяется со снимками нынешней версии (П-11).

Словари `src/i18n/dictionaries/*` остаются — в них переезжают строки интерфейса из
Приложения В ТЗ.

#### 0.2. Модель данных и правила предметной области

Чистый TypeScript, без Firebase. Делается до подключения базы, чтобы дальше всё

Требует ручных шагов George (раздел 4).

черновик», «Опубликовать», «Снять с публикации», «В архив», «Вернуть», «Дублировать»,
«Удалить» с подтверждением; галочка «Показывать в прошедших».

Подводный камень: дублирование и фотографии. План предполагал копировать файлы,
чтобы удаление оригинала не выбило картинки из копии. При реализации выяснилось,
что из браузера это невозможно: Cloud Storage отдаёт ссылки на скачивание без
заголовка `Access-Control-Allow-Origin`, поэтому прочитать байты файла нельзя, а
разрешающую политику задают только через `gcloud` или `gsutil`.

**Принятое решение: дубликат разделяет файлы с оригиналом.** Это безопасно,
потому что файлы в хранилище неизменяемы (путь содержит случайный идентификатор,
правка загружает новый файл) и ничего в приложении их не удаляет — удаление фото
из формы убирает только ссылку, иначе отмена правок забрала бы картинку у уже
опубликованной поездки. Уборка осиротевших файлов, когда до неё дойдёт дело,
обязана считать ссылки в любом случае: фотографии из `/assets/` уже общие.

Проверка: полный жизненный цикл поездки в Playwright; черновик и архив не попадают
в `out/` — проверяется поиском по собранным файлам.

#### 1.12. Пересборка сайта по кнопке «Опубликовать»

Требует ручных шагов George (раздел 4).

Появляется: воркер Cloudflare (`src/worker/index.ts`, `main` в `wrangler.jsonc`) с
точкой `/api/rebuild`, которая дёргает `repository_dispatch` в GitHub; отдельный
workflow сборки и выкладки; в админке — индикатор «Сайт обновляется…» и время
последней выкладки; cron ежедневной пересборки для перехода Upcoming в Past.

Подводные камни:

- Токен GitHub не должен попасть в браузер — он лежит в секретах воркера.
- Точка `/api/rebuild` доступна только вошедшему владельцу: воркер проверяет
  ID-токен Firebase.
- Две публикации подряд не должны запускать две сборки — ставим минимальный интервал.
- Добавление `main` в `wrangler.jsonc` не меняет способ отдачи статики: файлы
  по-прежнему уходят с edge, воркер для них не запускается.

Проверка: публикация из админки приводит к появлению страницы на тестовом адресе;
без входа `/api/rebuild` отвечает 401.

Критерии: А-08, А-09.

## 6. Реестр рисков

| Риск | Чем грозит | Что делаем |
| --- | --- | --- |
| Firebase Storage требует Blaze с картой | нельзя грузить фото | проверяем в пункте 0.3; запасной путь — стороннее бесплатное хранилище картинок |
| Доступ к EmailJS не получен | этап 2 стоит с пункта 2.1 | письма проверяются перехватом запроса, реальная отправка — после доступа |
| Лимит EmailJS 2 000 писем в месяц общий с ctmass.com | рассылка обрывается на середине | остаток показывается перед отправкой, отправка порциями и возобновляемая |
| Полный почтовый адрес не предоставлен | нарушение CAN-SPAM | адрес — поле настроек, рассылка блокируется, пока оно пустое |
| Пересборка при публикации | заказчик ждёт до 5 минут | предпросмотр в админке мгновенный, индикатор сборки в админке |
| Много фото у поездки | медленная страница | сжатие перед загрузкой, подгрузка по мере прокрутки |
| Спам в формах | мусор в базе и расход писем | Turnstile проверяется на сервере, запись в Firestore из браузера закрыта |
| Рост числа поездок | долгая сборка | перечень путей строится одним запросом, картинки соцсетей кэшируются |

## 7. Что в этой реализации не делаем

По разделу 12 ТЗ и по прямому решению заказчика:

- онлайн-оплата Stripe, waiver, статус «Paid» — этап 2;
- личные кабинеты посетителей, комментарии и отзывы;
- мобильное приложение, CRM, Telegram-бот, push-уведомления;
- перевод рассылки на почтовый сервис;
- написание и перевод текстов, фото- и видеосъёмка;
- ведение рекламы в Facebook.
